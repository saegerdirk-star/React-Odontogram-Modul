# React Advanced Odontogram

## Critical Defaults
- This is a **standalone React library** — it must work independently of DentalQuoteCreator
- Never introduce DentalQuoteCreator-specific dependencies or imports
- Preserve the public API (`OdontogramShell` props interface)
- All changes must maintain backward compatibility with existing integrations

## Architecture
- **React 19.2** + **TypeScript 5.5** — single-page interactive dental charting component
- **Vite 7.3** — dev server and library build
- **Tailwind CSS** — utility-first styling with custom theme via CSS variables (`--odon-*`)
- SVG-based tooth rendering with per-surface interaction

- The dental chart is **two grids, one per arch** (`.tooth-arch.upper-arch` / `.lower-arch` inside `#toothGrid`, built by `buildGrid` in `src/odontogram.ts`; each wrapper is `role="presentation"` so the listbox still owns the tiles). Every column in both arches is its own tooth plus 6 px — one rule, no hand-set values — so every contact is 10 px. The Class I canine relationship falls out of that: the same slack is added on both sides of every contact, so it cancels, and what is left between 13 and 43 is the anatomical difference (the lower six front teeth are 10 mm narrower than the upper six). The tip of 43/33 lands in the embrasure between the upper lateral and the upper canine because the teeth are the widths they are, not because anything was arranged. `ToothSpec.col_px` must agree with `grid-template-columns` (verify.py checks it) or the gum's papillae leave the joints
- `src/assets/teeth-svgs/` — **one template per position** since 2026-08-17: 16 permanent side views (11–18, 41–48), 10 deciduous (51–55, 81–85) and 20 occlusal (11/12/13/41/42/43 anterior plus 14/15/16/17/18/44/45/46/47/48/54/55/84/85 `_occl`), mapped by `TOOTH_TEMPLATE` / `PRIMARY_TEMPLATE` / `OCCLUSAL_TEMPLATE` in `src/odontogram.ts`. The opposite side is still the same file mirrored (21 from 11, 31 from 41, 61 from 51, 71 from 81) — nothing is shared ACROSS the jaws any more. Every one of them is GENERATED: `tools/toothgen/redraw_alle.py` and `redraw_occl.py` insert Dirk's drawn contour and pulp into a DONOR template that supplies the ~200 clinical layers. Never hand-edit one. The permanent side views are inlined as `?raw` imports; the deciduous and occlusal ones load on demand (`import.meta.glob`), so a chart pays only for the artwork it mounts
- `tools/toothgen/README.md` — the toolchain in full, rewritten 2026-08-19 (it had stood at "nine templates from four source drawings" and described a tool that no longer exists). The short version:
- `tools/toothgen/` — **three stages, two contracts.** `npm run toothgen:redraw` runs ALL THREE (`toothgen:flaechen` is the third, `flaechen_einsetzen.py`); until 2026-08-19 it stopped after the second, and running the documented command silently dropped the derived filling/caries surfaces back to the donor's shapes — both are valid SVG, so no contract complained. `build.py` (+ `occlusal.py`) generates the Schumacher-derived templates into `tools/toothgen/spender/` — not versioned, reproducible, `npm run toothgen:spender`. Those are the DONORS. `redraw_alle.py` / `redraw_occl.py` (`npm run toothgen:redraw`) then insert Dirk's drawn contour and pulp and write what actually ships. **The rule the whole redraw arc converged on: what is drawn gets INSERTED; only what nobody draws is warped.** It is not unlimited — deriving the veneer by WARPING made it worse (see `veneer_aus`); the veneer is instead CUT from the crown outline (see `kronen.py` below). `redraw_plan.py` holds both target→drawing→donor tables and nothing else, so a check need not import a generator. `verify.py` measures the DONORS against `spec.py` and its frozen digests (unchanged by the redraw); `verify_redraw.py` is the contract for the shipped set — layer inventory identical to the donor, one continuous contour, lumen inside the root, the implant body not stretched, the gum drawn for the column the tooth actually stands in, and the occlusal plane on one line, and — since odontogram-8i5 — that every layer stays HORIZONTALLY inside the contour (`bleibt_im_zahn`). That last one is the check whose absence let 35 layers at 46 be warped up to 9.4 units clear of the tooth without a single contract noticing: inventory, contour, lumen and occlusal plane were all unchanged, the damage sat one layer further on. `TOL_INNERHALB` = 3.0 is READ OFF the distribution (median −0.64, 99 % under 1.59, then a gap up to a cluster between 3 and 9.6), and the pre-existing overhangs are frozen in `BEKANNTE_UEBERSTAENDE` (42 at first, 19 after odontogram-8i5 was fixed — the check reported those 23 as clean itself) — a contract that is red from the start checks nothing. A frozen entry that becomes clean is ALSO reported, so the list can only shrink. `npm run toothgen:verify` runs both plus `check_roundtrip.py` and `verify_hoecker.py`. **`verify_hoecker.py` is the one check that runs under `python3`, not `uv run`** — it re-runs `hoecker.gebiete()`'s flood fill over each SHIPPED occlusal template (outline `background-cusp` + the `fissure` layer) and compares the field count and area shares against a frozen table. It exists because on 2026-08-20 the fissure pattern broke TWICE while widening the premolar occlusal views and no contract saw it: layer inventory, contour, occlusal plane and even the `fissure` path count were all unchanged — the damage sat one layer further on. The cause is still there: `redraw_occl` identifies the outline as THE PATH WITH THE MOST POINTS, and after a re-serialisation a cusp can overtake it. Also note **the chain is not bit-reproducible**: a run with no change shifts coordinates by up to 0.02 units, so `git status` cannot tell whether a run changed anything real — which is why the shares are frozen with a three-point tolerance rather than exactly. `spec.py` records the per-class anatomy (root count, root fraction, crown ratio, furcation), `verify.py` re-measures the generated assets against it and against frozen geometry digests, `check_roundtrip.py` proves path serialization is lossless. `crown_width` (outline extent) and `silhouette_width` (tooth material) are DIFFERENT measurements and must not be swapped — a crown width is the first, the root that has to hold a canal is the second. `fillings.py` stretches the mesial and distal filling shapes until they meet the occlusal one, so MO/OD/MOD draws as ONE restoration (`verify.py` fails if a pair stops being one connected shape); the buccal shape is deliberately left separate. **A SYMBOL IS CONSTRUCTED, NOT MAPPED** (odontogram-7xl): `symbole.py` writes the extraction cross as the two DIAGONALS of the tooth's box (side view the contour, occlusal the table) — a cross is not a drawing, it is a construction, and one that is constructed comes out right on every template with no field, no donor and no drift. Only the `d` is replaced; layer, id, path count, order and style stay, so the layer inventory and the fingerprint are untouched. For the symbols nobody would construct, the weaker rule still holds — **a symbol is not anatomy**: `extraction-plan`, `crown-needed-path` and the three mobility grades go through `redraw_apply.starr_im_rahmen` — uniform scale plus translation from the donor contour's box to the inserted one's, NO rotation. A thin-plate spline bends straight lines: the extraction cross ran as two wavy bands down the roots (up to 49 units off its own chord). The implant body and the pins were exempted for the same reason long ago (`starr_aus`, which derives a rotation from a long axis) — that one is wrong for a symbol: a cross that tilts with the tooth is not a cross. Crown silhouettes (`crown-needed-shape`, `crown-replace-shape`) and `crown-leakage` stay on the tooth field — they DEPICT something. Put the PATH in that list, never the enclosing `<g>`: `crown-replace` contains only the silhouette, and listing the group pushed it off the tooth on nine templates. `gum.py` DRAWS `gum-base` and `bone-base` outright, in final coordinates, instead of warping them out of the sources — the only way to make the gingiva read as one line across the arch, since a papilla is shared between two teeth and two hand-drawn halves cannot agree on its height. Its papilla sits half a column plus half a grid gap from the tooth's centre, so two neighbours meet on the same point; `ToothSpec.col_px` holds that column width and `verify.py` checks it against `grid-template-columns` in `src/index.css`. **Both boundaries of the band hang on the tooth's OWN cervical line** (`redraw_plan.ZERVIKAL`, 26 frozen heights re-measured by `verify_redraw.py`): the crest `CREST_BELOW_CEJ` = 3.85 units apical of it, the papilla tip at `PAPILLA_FRAC` = 0.75 of the crown length above the occlusal plane. They used to be one number each for the whole arch, because "neither template knows which tooth it will stand next to" — true until 2026-08-17, when every position got its own template. The caller now passes the height per JOINT and both neighbours compute the same one. At the CREST that joint value is the MINIMUM of the two, not the mean: the interdental septum is the coronal-most part of the bone, and it is also the condition under which the edge stays smooth across the joint — every band overhangs 3 units into the neighbour's column, the APICAL edge is the one that shows, so a neighbour that falls away from the joint hides the overhang completely while one that rises leaves a step (measured: 1.2 units). The flat 36.0/19.0 gave a band 8.7 units tall at 41 and 3.1 at 43, and put the papilla APICAL to its own margin on all ten deciduous teeth. The DONORS keep the flat fallback — their band is overwritten in the redraw, so `verify.py`'s frozen digests stay put. **The THIRD stage inserts the surfaces a finding is charted on**, after the contour is in place, because they are derived FROM the drawn contour and cannot be warped out of a donor: `fuellflaechen.py` derives the mesial/distal/occlusal (incisal on an anterior) boundaries from Dirk's drawn boxes into layer `4 FUELLFLAECHEN (abgeleitet)` — a hand-drawn shape always beats a derived one; `fuellflaechen_einsetzen.py` rasterises those regions and writes them into the shipped template (serialise with TWO decimals — the chain re-serialises at `prec=2`, and three decimals fail `check_roundtrip.py`); `kauflaechen.py` does the same for the occlusal view, cutting the table along the drawn fissures and projecting the buccal WIDTH back onto the side view; `halsbaender.py` draws `caries-root`/`caries-subcrown` as analytic horizontal slabs at the neck rather than warping them; `kronen.py` cuts the CROWN out of the inserted contour instead of warping a separately drawn cap onto it — the cut sits at `redraw_plan.ZERVIKAL` (no second table: that one already carries the gum band, and a number beside it is where the two drift apart), the occlusal view takes `background-cusp` whole because it has no neck to cut at, and the inner telescope crown is the same shape contracted about the midpoint of the cervical line. Deriving the neck from the outline alone (narrowest point between the crown's widest and the root) was tried and rejected: on a multi-rooted tooth it finds the APEX, where the width goes to zero. `endo.py` does the same one field further in (odontogram-7xl): what lies in the CANAL is cut from the INSERTED pulp — `endo-filling`/`endo-medical-filling` are the lumen itself, `endo-filling-incomplete` the lumen shortened apically by 18 %, the two pins its coronal 45 %, and `endo-resection` the severed apex cut from the CONTOUR. Warped, the root filling stood 12.4 units right and 18.1 below the pulp at 16 and drew a tangle across the crown. Unlike the crown cut it keeps EVERY connected run, not the longest: a multi-rooted lumen falls apart into several canals apically, and dropping one would leave a canal unfilled — they ride as subpaths in ONE `d`. `crownprep.py` cuts the PREPARED tooth (`tooth-crownprep`) out of the contour the same way, but along a line derived PER TOOTH from the inserted pulp so the prep can never reach it: `max(crown tip − 2 mm, pulp roof + 1.2 mm)` — where the pulp stands high (41/42, deciduous) it automatically reduces less, which is clinically exactly right, and the crown walls run mildly convergent to the flat cap (Dirk's call) while the root stays full. It was a warped donor silhouette blind to this tooth's pulp, and lay up to 2.7 units APICAL of the pulp roof on eight templates (12/13/14/15/43/45/53/83), where the runtime clip then amputated the pulp flush — reading as an opened pulp. `verify_redraw.py` now checks the prep face stands coronal to the pulp roof (`TOL_PULPADACH`), and — like `endo.py` — it runs AFTER the pulp, so it stays correct when the pulps are redrawn (a planned young-adult redraw raises the horns; the prep line follows). `crown-needed-shape`, `crown-replace-shape` and `crown-leakage` are derived too (odontogram-7xl): the first two ARE the crown's shape, and the third is a slab on the cut line, because a margin finding belongs at the margin and the margin is that line. Inlay and onlay are NOT derived — they cover the tooth only partly. **The VENEER, though, IS derived since 2026-08-23 (odontogram-5hm, Dirk "aus Kronenschnitt, eingerueckt"):** `kronen.py` `veneer_d` insets the crown chain by `VENEER_VERSATZ` = 1.6 units along the INWARD NORMAL (a constant offset, not the inner-telescope SCALE, which shortens a tall incisor vertically; the normal is found once from the winding, not per-point from the centroid, and folds at a sharp incisal corner are dropped greedily) — so the veneer IS the contour, inset, with a visible tooth rim, and the pointed edge closes because it is cut from the outline. This is NOT the row-scan `veneer_aus` (which ran to the tooth edge and cut the tip flat, both rejected). In the OCCLUSAL view `kauflaechen.py` `veneer_einsetzen` writes only the BUCCAL rim band of the table (Dirk: "nur den Rand nach vestibulaer") — the same `gebiete()['buccal']` mask as the buccal filling surface; a veneer-only pass, not a full `einsetzen`, because the raster filling surfaces are not bit-reproducible. Every veneer gets its material's crown dome (`odonKrone…` in `index.css`) and the softened `#a2937e` stroke (the template gave it the Gradia green `#1b3f1c`). `draufsicht.py` reads an anterior top-view drawing BY CONTENT (largest closed path = outline, open paths = lines), checks Dirk's `v`/`m` orientation marks against the documented convention, and normalises it to the side view's crown width as `<tooth>_occl_norm.svg`. Supporting modules, called by the above rather than run directly: `roots.py` (root topology before the common transform), `svgpath.py` (path parse and serialise), `graft.py`, `hoecker.py` (raster flood-fill planar subdivision of a drawn occlusal table), `redraw_apply.py` (the insertion itself)
- `src/assets/icon-svgs/` — UI icons

## Tooth State Model
Each tooth has:
- `toothSelection`: tooth-base | missing | implant | pontic
- `toothSubstrate`: natural | radix | broken | crownprep
- `restorationType`: none | crown | inlay | onlay | veneer | bridge (implant-gated crowns/bridges compose with an implant connector layer). Restoration options are gated by tooth kind via `restorationOptions()` (`src/registry/restorations.ts`): an implant tooth offers only crown/bridge, plus the five `prosthesis` attachment entries; a missing/gap tooth (`toothSelection === "none"`) offers only a bridge pontic, plus the two removable-denture `prosthesis` entries; a `radix` substrate hides the restoration control entirely (`restorationRowHidden()` in `src/odontogram.ts`) — no restoration can be authored on a root remnant. A `bridge` restoration renders both the crown cap AND the saddle-connector layer via `composeRestorationLayers()`; the multi-tooth bridge-span overlay connector is arch-aware (mirrored saddle-Y fraction for the lower arch, `SADDLE_Y_FRACTION_LOWER` in `src/bridgeOverlay.ts`), and applying a bridge via a Statuses preset explicitly re-triggers the overlay recompute. **Bridge look reworked (odontogram-5hm):** a Krone–Brückenglied–Krone entry (crown-abutment beside the pontic, Dirk's "Pfeiler = Krone") is joined as ONE span via `bridgeConstructions` (over `checkBridgeSpans`, which takes the crown neighbours in) rather than `detectBridgeSpans` (adjacent-pontic runs only), so a single pontic between two crowns actually connects. The connectors are solid blocks at the contact point (never overshooting occlusally, kept clear of the gingiva) carrying a per-material radial gradient (`ensureBridgeGradient`) in the ACTUAL displayed crown colour (`DEFAULT_MATERIAL_COLORS` re-aligned to the templates). The pontic is no longer a flat-cut cap: its cervical strip is CLIPPED (`syncPonticMark` stamps `data-pontic` on the tile, `clip-path` in `index.css`, computed in the tile's OWN frame like the onlay clip) so the crown floats as a Brückenglied with a narrow gum strip drawn beneath it in the overlay (filled with the shown gingiva colour). The per-tooth `{material}-bridge-connector` saddle layer is hidden (`display:none`), the shared crown outline stroke softened off the hard red `#b3261e`, and the emax ramp recoloured white/cream (was orange). All of it is `fill`/`stroke`/`clip-path`/`data-*` → outside the SVG fingerprint (id/opacity/class), parity byte-identical
- `restorationMaterial`: none | emax | gold | gradia | zircon | metal | metal-ceramic | telescope | temporary
- `prosthesis`: none | healing-abutment | locator | locator-denture | bar | bar-denture | removable-partial | removable-full — orthogonal implant-attachment / removable-denture axis, surfaced as "Kivehető:" entries in the combined restoration dropdown (gated per tooth kind — see `restorationType` above)
- `crownLeakage`: boolean — marginal-leakage finding, shown only when `restorationType` is crown or bridge. Both the tooltip (`getStateSummary`) and whole-mouth summary (`getOdontogramSummary`) gate this line on the exact same predicate as the `#crownLeakageRow` control (`!restorationRowHidden(state)` AND crown/bridge), so a tooth with a stale crown/bridge payload but a hidden restoration row (radix/milktooth/extraction/under-gum) never shows a leakage line the control itself doesn't display
- `endo`: none | endo-medical-filling | endo-filling | endo-filling-incomplete | endo-glass-pin | endo-metal-pin — mutually exclusive with `pulpDx`; both are surfaced through one merged "Pulp / Endo status" selector (vital vs. treated groups), and setting `endo` to a treated value normalizes `pulpDx` to `normal` (suppressing the diseased-pulp glyph)
- `rootFracture`: none | vertical | horizontal, and `rootResection`: none | hemisection | amputation | premolarisation, each with a `*Root` qualifier (beads odontogram-t6y / -ca0). The three `broken*` flags mean the CROWN; a broken ROOT is a different finding, and vertical vs horizontal decides whether the tooth can be kept. `rootResection` is NOT `endoResection` (that is the apicoectomy — apex cut, tooth whole). `rootsOf(toothNo)` NAMES a position's roots (upper molar mesiobuccal/distobuccal/palatal, lower mesial/distal, 14/24 buccal/palatal), position-based like `furcationEntrances`; empty means single-rooted. A root is PRESELECTED on a multi-rooted tooth: "unspecified" draws as "middle", which on a lower molar is BETWEEN the roots, and a hemisection with no named root drew nothing — both looked like a bug. **Rendered outside the tooth SVG**: the fracture line in an overlay IN FRONT of the tiles (`svg.fracture-lines`), the hemisection as a `clip-path` on the tile (side in `data-hemi-side`, shape in CSS) — a shadow can be laid on, but taking something away needs a clip. Parity byte-identical. The palatal root of an upper molar cannot be cut away: in a buccal view it stands BEHIND the buccal one and has no side of its own — which is why a hemisection is usually a lower tooth. Payload 2.27
- **Never measure `gum-base`/`bone-base` inside a tile**: they are `display:none` there (the clone in the overlay is what is drawn), and a hidden element's `getBoundingClientRect()` is all zeros. That silently killed the cervical shading and sent the fracture line across the whole chart. Measure the CLONE in `svg.gum-overlay` (stamped `data-tooth`/`data-layer`) or the tile rect.
- `sensibility`: none | vital | no-response | questionable, and `percussion`: none | negative | sensitive — the pulp TESTS beside the AAE diagnosis they feed (bead odontogram-fu1). The reason in one sentence: `apicalDx` separates symptomatic from asymptomatic apical periodontitis, and what separates those two IS percussion tenderness — the conclusion was charted, the test was not. TWO axes, not one: a vital tooth can be tender to percussion. `none` means NOT TESTED, never "unremarkable", which is why percussion carries its own `negative` — tested and not tender is a finding, and without it the diagnosis below cannot be justified. `sensibilityAllowed` needs a present natural/milk tooth (an implant has no pulp); `percussionAllowed` INCLUDES the implant, where tenderness is a peri-implant sign. Both guards run BEFORE the DS-1 gate (like `setRetention`), so they bind the keyboard too. Deliberately NOT in `fhir/dentalCoreContract.ts` — no generated property is verified for either, and inventing one would break the same rule under which odontogram-c51 ships no unsourced norm; local codes only. No `svgLayer` → parity byte-identical. Payload 2.26
- `pulpDx`: normal | reversible-pulpitis | irreversible-pulpitis | necrosis — AAE pulp diagnosis (replaced the retired `pulpInflam` boolean); mutually exclusive with `endo` (see above); `reversible-pulpitis` renders a reduced pulp glyph
- `pulpLatin`: none | pulpa-sana | hyperaemia-pulpae | pulpitis-acuta-serosa | pulpitis-acuta-purulenta | pulpitis-chronica-clausa | pulpitis-chronica-ulcerosa | pulpitis-chronica-hyperplastica | necrosis-pulpae | gangraena-pulpae — practical-Latin pulp subtypes, surfaced by the pulp picker only when the `pulpDetailLevel` setting (`simple` | `aae` | `latin`, default `aae`) is `latin`. `setPulpDetailLevel()` calls `notifyStateChange()`, so switching the level live-refreshes the whole-mouth summary and every tooth's tooltip immediately instead of staying stale until the next tooth edit
- `apicalDx`: normal | symptomatic-apical-periodontitis | asymptomatic-apical-periodontitis | acute-apical-abscess | chronic-apical-abscess | condensing-osteitis — drives the periapical glyph directly, decoupled from the `mods.inflammation` modifier. The `mods.inflammation` toggle (`syncInflammationModVisibility()` in `src/odontogram.ts`) is shown ONLY for missing (`toothSelection === "none"`) and extraction-socket (`no-tooth-after-extraction`) teeth — it is hidden on present teeth (where `apicalDx` drives the glyph) and on implants (where `periImplant` drives it instead)
- `periapicalType`: none | granuloma | cyst — periapical lesion subtype qualifying the `apicalDx` glyph, offered by the picker only under symptomatic/asymptomatic apical periodontitis; the legacy `abscess` value is still accepted/stored (folded into `apicalDx` on import) but no longer authorable, since it duplicates the apical diagnosis
- `resorptionType`: none | internal | external-cervical — replaced the retired `rootResorption` boolean
- `periImplant`: none | mucositis | peri-implantitis-mild | peri-implantitis-moderate | peri-implantitis-severe — implant-only peri-implant status (2018 World Workshop staging); `mucositis` reuses the existing periodontal gum glyph, `peri-implantitis-*` additionally activates the `peri-implant-bone-loss` layer at severity-scaled opacity (0.4/0.7/1.0); retires the implant `mods.inflammation` periapical glyph (missing/extraction-socket teeth are unaffected) and hides the inflammation/parodontal modifier checkboxes on implants
- `mods.mobility` (M1/M2/M3 grades): drawn as a ROMAN NUMERAL I/II/III in the tile's bottom-left corner since 2.35.0 (odontogram-7xl, Dirk's proposal), not as SVG artwork. The old glyph could not express the grade at all: the `mobility` group has exactly two children, both always active, and was switched on as a whole — M1, M2 and M3 drew the same picture. `updateToothMobilityMark` stamps `data-mobility` on the tile DIV and CSS draws it with `::before` (the retention mark next to it uses `::after`; they share a tile and must not displace each other). Outside the SVG, so the fingerprint never sees it. The mobility control is hidden/disabled on implant teeth (`mobilityRowHidden()`/`mobilityDisabled()` in `src/odontogram.ts`) — implants don't carry periodontal mobility
- `caries`: array of surface identifiers (mesial, occlusal, distal, buccal, lingual)
- `fillingSurfaces`: array of filled surfaces
- `rootCaries`: none | active | arrested | active-cavitated — wires the `caries-root` artwork layer on a present tooth, at an opacity driven by severity (`active` 0.5 / `arrested` 0.7 / `active-cavitated` full)
- `caries`/`fillingSurfaceMaterials`/`cariesSeverity`: caries is a per-surface **state machine**, not two independent fields. `cariesSeverity` (0-6) is the single unified per-surface severity — replacing the old separate `cariesDepths` (ICDAS) and `secondaryCaries` (CARS) fields. A surface in `caries` with **no** filling on it renders as primary caries (`caries-{surface}`, ICDAS-tiered opacity from `cariesSeverity`); the same surface **with** a filling present renders as recurrent caries instead (`subcaries-{surface}`, CARS-scored opacity from `cariesSeverity`) — a surface is never both at once. A contextual popup shows only the severity group relevant to the surface's current state (primary ICDAS-depth group when unfilled, CARS group when filled)
- `radiographicDepth`: per-surface none | E1 | E2 | D1 | D2 | D3 — radiographic caries depth, independent of the visual ICDAS/CARS severity scale (`cariesSeverity`); surfaced as a `data-radio` badge attribute
- `fillingDefect`: per-surface none | marginal | fracture | wear — filling-defect finding on a DIRECT restoration (marginal defect/overhang, fracture/chip, or worn/deficient material), independent of recurrent caries; gated to surfaces present in `fillingSurfaceMaterials` (only a filled surface can carry a defect). Authored via a left-side per-surface indicator on the Fillings card (mirrors the right-side caries-depth indicator); renders on the chart by activating the existing `defect-{surface}` artwork layer; shown in the tooltip and the whole-mouth fillings summary, labeled explicitly (`fillingDefect.label` prefix) the same way recurrent caries is labeled on the Caries summary line. Payload version 2.7
- `wearEdge`: none | attrition | erosion — incisal/occlusal tooth-wear type; `wearCervical`: none | abrasion | abfraction | erosion — cervical tooth-wear type. Replaced the two on/off bruxism-wear flags (`bruxismWear`/`bruxismNeckWear`); authored via two dropdowns on the wear row. Render the existing `tooth-bruxism-wear`/`tooth-bruxism-neck-wear` layers (no new SVG), gated on `toothSelection === "tooth-base"` + `restorationType === "none"` + `toothSubstrate === "natural"`. Shown in the tooltip and a dedicated whole-mouth "Wear" summary section. Payload version 2.8; a legacy edge-wear flag migrates to `attrition`, a legacy cervical-wear flag migrates to `abrasion`
- `discoloration`: none | tetracycline | fluorosis | nonvital | extrinsic | other — per-tooth discoloration cause. Tints the shown natural crown's fill (`tooth-base` or `milktooth-base`, whichever is active) a cause-specific colour at render time; gated on a natural, unrestored tooth-base or milk tooth (`toothSelection` tooth-base or milktooth + `restorationType === "none"` + `toothSubstrate === "natural"`). Fill is not part of the SVG-fingerprint parity check (only id/opacity/class are), so the tint is parity-safe. Shown in the tooltip and a dedicated whole-mouth "Discoloration" summary section. Payload version 2.9; additive, no migration needed
- `orthoAppliance`: none | bracket | band; `orthoDrift`: none | mesial | distal; `orthoVertical`: none | extrusion | intrusion (extrusion renders an arrow-up glyph, intrusion an arrow-down glyph); `orthoRotation`: boolean — per-tooth orthodontic charting axes. Reuse the dormant v2.5.0 ortho artwork (no new SVG); gated on a present natural tooth (`toothSelection` tooth-base or milktooth — the shared `orthoAllowed` predicate). ## Periodontal Data (perio sub-record)
- Each tooth state carries a `perio` sub-record — `{ pd: Map<site,mm>, gm: Map<site,mm>, bop: Set<site>, sup: Set<site> }` over the six standard sites `PERIO_SITES = ["MB","B","DB","ML","L","DL"]` (buccal row, then lingual row). Kept SEPARATE from the 5-surface caries maps (different site convention). First sub-project (P1) of the periodontal-parameters arc; later sub-projects add the perio-chart grid UI, SVG recession/furcation rendering, and 2017 staging/grading.
- **Semantics:** absence = "not charted", NOT zero. A site is charted once its `pd` is set; `gm` (gingival margin vs CEJ, SIGNED: recession +, coronal/pseudopocket −) defaults to 0 when `pd` is set but `gm` unset. `setPerioSite(toothNo, site, {pd?,gm?,bop?,sup?})` validates + clamps (pd int 1–15, gm int −10…+20); `pd` null/`<1` un-charts the site (atomically clears pd/gm/bop/sup for it — no orphans).
- **Derived, never stored:** `CAL = pd + (gm ?? 0)` (`getToothCal`); recession = `max(gm,0)`; pseudopocket = `max(−gm,0)`; whole-mouth `%BOP = (charted sites ∩ bop) ÷ charted sites` (can't exceed 100 — BOP on an un-charted site is ignored). `getPerioSummary()` returns charted/bleeding counts, %BOP, worst CAL, max PD. Public API: `setPerioSite`/`getToothPerio`/`getToothCal`/`getPerioSummary`/`getPerioChart`. `getPerioChart`/`getToothPerio` are OMIT-WHEN-EMPTY (uncharted sites have no key — default them like `radiographicDepth`).

## Tiefenwirkung (Dirks Frage vom 2026-08-20)
- The teeth were FLAT because the tooth substance is one colour: `tooth-base` carries an inline `fill: #ebebeb` and `tooth-base-beauty` is two FLAT white shapes. The eleven linear and eight radial gradients in a template all belong to the restoration materials.
- Two cues, one switch (`getToothDepth`/`setToothDepth`, Settings -> Tooth details, session state like `perioViewMode`): a **body gradient** across crown and root (defined ONCE in `App.tsx` under `<defs>`, `objectBoundingBox` maps it onto every shape) and a **cervical shading** where the tooth enters the gum. OFF drops the `odon-depth` class on `#toothGrid`, so the `!important` fill rules stop applying and the shade overlay is removed — **no JavaScript in the render path**, same construction as the restoration palette.
- The body gradient is **SYMMETRIC on purpose**: the left quadrant is the same drawing MIRRORED, so a gradient with a light and a dark side would light that half from the other direction. A narrower, darker rim was tried and rejected — the contour already has its own `stroke`, and a second hard edge beside it only doubles the line.
- The cervical shade is a SECOND overlay `svg.gum-shade` appended LAST (in front); the gum bands sit behind the grid because they are behind the teeth, but a shadow falls ON them. Its height comes from `gum-base`'s own coronal edge, never a set number, so it follows a changed gingiva.
- **The cusps were already there.** An occlusal template carries every cusp field as its own shape under `tooth-base` (six on an upper first molar) — but with a LINEAR gradient, a ramp rather than a dome. A shared `radialGradient` mapped per shape by `objectBoundingBox` turns each into a dome. Two traps: `background-cusp` (the outline) must be excluded via `:not([id])` or the whole table becomes ONE dome, and the fissure strokes via `:not([style*="fill: none"])` or an `!important` fill turns lines into areas and paints the table over.
- **Only the tooth substance is shaded — with ONE exception since 2026-08-21.** Colour carries meaning here; shading over a caries or a filling would change how a finding reads. The CROWN is the exception (odontogram-5hm, Dirk's call): its dome's MIDDLE STOP is exactly the configured colour, so the statement is unchanged and only lit, and all three stops run through the palette variable so a chosen colour gets ITS dome. Not tied to the `odon-depth` switch — that shading is a reading aid one must be able to switch off, a crown's volume is the material itself. Each stop is written TWICE on purpose: the attribute carries the computed fallback, the style declaration the `color-mix`, so a browser without `color-mix` drops the declaration and keeps a valid colour instead of painting the crown black.
- Parity-safe BY CONSTRUCTION: `collectActiveLayers` skips everything under `<defs>` and every gradient element, and records only `id`/`opacity`/`class` — not fill. What would NOT be safe is a new VISIBLE element with an `id`.

Same documented limitation as `detectBridgeSpans`: two bars in one arch merge, since state carries no per-bar grouping id.
- **Render lives in the GRID overlay, never in a tooth's SVG** → SVG-fingerprint parity byte-identical. `updateRetentionBarOverlay()` (called from `updateBridgeOverlay`) draws into its own `svg.retention-overlay` using the SAME `tileRectFor` geometry the bridge saddle reads, so the two can never disagree about where a tooth is. `computeRetentionBars` draws ONE run per span (gap-by-gap would break at every tile boundary — the failure `detectBridgeSpans` exists to prevent) at `BAR_Y_FRACTION` 0.62, above the crown at the gingival margin. `computeClaspGlyphs`/`claspPath` draw a QUARTER arc whose centre sits at the crown's occlusal-inward corner, so one end lands at the height of contour, the more occlusal end at the interdental space, and the belly faces the gingiva — all three from one construction. Two directions drive it from DIFFERENT sources: inward is the engaged SIDE (`mesialIsLeft`, quadrant 2/3), occlusal is the ARCH (lower draws crowns up), and the arc's rotational sense is derived from their product rather than tabulated. `CLASP_EDGE_INSET` anchors the proximal end inside the tile edge, since a tile is wider than the crown it holds.
- `retentionMark()` is charly's own shorthand, read off its keypad rather than paraphrased: `<Kl`/`Kl>` (angle brackets), `( G`/`G )` (ROUND brackets — the bracket shape is vocabulary, not decoration), and `ste` for the bar with no bracket at all (a bar does not engage one side of one tooth). Only the attachment and the bar use it as a tile badge; the clasp is drawn.

## Provenance: what the patient arrived with (odontogram-ap7)
- **DERIVED, never stored.** The dated examination archive (odontogram-2vd) already holds the mouth as the patient brought it, so "pre-existing" is a comparison against the EARLIEST archived examination — no payload bump, no FHIR mapping, and no second record that could drift out of agreement with the archive. It compares `charts.status` EXPLICITLY, never the active-chart alias: an examination records what was observed, and provenance is a fact about the past a proposal cannot change. API: `getBaselineExamination()`, `getPreExistingAxes(toothNo)`, `getChangesSinceBaseline()` (same `PlanChange[]` shape/order as `getPlanChanges`), `isToothPreExisting(toothNo)` (the question `odontogram-im1` consumes — an implant present at the baseline arrived with the patient, so an empty implant product on it is a complete record rather than a gap).
- **`PROVENANCE_AXES` = `DIFF_AXES` + `fillings` + `caries`.** `DIFF_AXES` is deliberately NOT extended: it answers "what does the plan change", where a filling and a caries lesion are not treatment-plan axes, and growing it would silently change the "What changes" box. An axis only counts as a finding when its label differs from what a HEALTHY `defaultState()` tooth reads (`axisCarriesFinding`) — a `planChange.none` sentinel test alone reports every healthy tooth as carrying two findings, since `presence` reads "Tooth" and `substrate` reads "natural".
- **Render (`applyPreExistingStyling`, run in `applyStateToSvg`'s roots loop AFTER `applyProposedStyling`):** hatches the layers active NOW that were also active in the baseline, minus the anatomy a healthy tooth draws (`healthyLayerIds`, cached per template+tooth). Marking goes through `style.fill` → a `<pattern>` in `<defs>` whose background is the shape's OWN colour (`fillLightness` parses BOTH `#rgb` and `rgb(...)` — `style.fill` reads back normalized, so hex-only would drop the colour on every real layer) and whose line colour flips dark/light by luminance. `data-base-pfill` capture-once + symmetric `clearPreExistingStyling`, mirroring the proposed-styling and SP12 discoloration pattern. Gated on `chartMode === "status"` (Plan mode leaves the tooth to the dashed channel) AND an archive existing — the parity fixtures archive none, so the capture never runs it; `style.fill` is in neither the SVG fingerprint (id/opacity/class) nor `tools/toothgen/verify.py`'s frozen geometry digests, so hatching is parity-safe on both contracts.
- **The hatch marks WORK, never the tooth and never the disease** (`isRestorativeLayer`): composed restorations (`allRestorationLayers()` + the per-material wrapper `<g>`s), direct fillings (`filling-` prefix), endodontic fillings/pins, apicoectomy, fissure sealing. A radix or an implant is a tooth, not work; caries/calculus/periodontal findings are disease. `isActiveWithin` skips anything switched off between the shape and its layer, so the wrapper `<g id="gold">` no longer paints its inactive `gold-inlay`/`gold-veneer`/`gold-bridge-connector` siblings. The DERIVATION stays broad — the chart narrows, the record does not.
- **`repaintForBaselineChange()`** runs on `captureExamination`/`resetExaminations`/`removeExamination`: a new baseline changes what EVERY tooth means, exactly as a chart-mode switch does. Without it hatching appeared only on teeth edited afterwards. No-ops when no grid is mounted (`toothSvgRoot.size === 0`).
- **Correcting the initial examination** (Dirk's choice over a per-tooth override — one account of what the patient arrived with, not a second note beside it): `beginBaselineCorrection()` / `commitBaselineCorrection()` / `cancelBaselineCorrection()` / `isCorrectingBaseline()`. The round trip lives in `odontogram.ts`, NOT the UI, because `loadExamination` replaces the live case — entering without stashing today's findings would DESTROY them. `commitBaselineCorrection` passes the examination's OWN id, which `captureExamination` replaces in place, so it keeps its identity and date. The stash is runtime-only and never serialized, so the UI must make the mode unmissable (`#baselineCorrectionBanner`).
- **Import (`importAsBaseline`, session flag, default ON, never serialized):** a chart arriving by import carries no archive, yet everything in it is pre-existing from this practice's view — the normal way a foreign chart enters. `adoptImportAsBaseline(broughtItsOwnArchive)` archives it as the initial examination dated today, and is called from BOTH `importStatus` and `__importStatusForTest` but deliberately NOT from `hydrateImportedCharts` (every load goes through that, including `loadExamination` and the correction round trip, where archiving would file an examination mid-correction). `broughtItsOwnArchive` is read BEFORE hydrating, since hydration replaces `examinations`. A document that brought its own archive keeps it, so a re-import is never re-dated over the patient's real intake date. Surfaced as a checkbox in the import menu (the file picker is the OS's, so the menu is the only place to ask). `getImportAsBaseline`/`setImportAsBaseline`.
- UI: `src/ExaminationCard.tsx` (`#examinationCard`, mounted at the top of the control panel) — capture with a date, the baseline named, the archive list, and the correction round trip. It subscribes to `onStateChange` itself, like `PerioChart`/`PerioSidebar`.

## Orthodontics (bead odontogram-c51 and children)
- **Model analysis (c51.1)** — `src/modelAnalysis.ts`, dependency-free and pure like `perioClassification.ts`. `deriveModelAnalysis({widths, absentTeeth})` returns the six sums, Tonn / Bolton-anterior / Bolton-overall as `RatioIndex` (actual, target, delta, which arch carries the excess and by how many mm), the Tonn target incisor sums, and `substitutions`. Norm constants carry their publication beside them (Tonn 1937 → 74,0 %; Bolton 1958 → 77,2 % / 91,3 %). **A sum whose teeth are not ALL measured is `null`, never a partial total.** The millimetre figure is the CLASSICAL Bolton excess, deliberately not the reference printout's `delta% × numerator` — both are documented and a test pins the divergence.
- **Contralateral substitution** — a tooth that is not on the model borrows its partner's width (`contralateral()` mirrors FDI quadrants 1↔2, 4↔3, 5↔6, 8↔7). Driven by `isToothMeasurable(toothNo)` in `odontogram.ts`, which is FALSE for `none` / `not-erupted` / `no-tooth-after-extraction` / `tooth-under-gum`, and for an implant UNLESS it carries a crown or bridge (Dirk's ruling; he notes it has not arisen in thirty years). An absent tooth NEVER uses a width stored against itself (ignored, not deleted); substitution never chains. Every borrowed width surfaces in `substitutions` and renders read-only, tinted and listed — an inference must never read as a measurement.
- **Cephalometry (c51.2)** — `src/cephalometry.ts`, three layers: `LANDMARKS` (anatomic / radiographic / constructed), `MEASURES` over them, and `PROFILES` selecting from those. **Norms belong to the PROFILE** (`CephProfile.norms`, resolved by `normFor(measureId, profileId)`), because schools disagree — ML-NSL is 28° in Hasund and 32° in Segner, and the same value reads vertical against one and neutral against the other. A profile declares its own `referenceFrame`, including `"none"` so Sato's Denture Frame Analysis stays representable. **Four profiles ship** (Dirk, 22.08.2026): `hasund` against the anterior cranial base, `ricketts` against the FRANKFURT horizontal, which is why `Po`/`Or` are in `LANDMARKS` at all, `jarabak` (the S-N-Ar-Go-Me polygon), and `steiner`. **Steiner and its whole further catalogue come from the practice's own FRWin software** (Dirk exported it as text into `~/dev/Odontogram-Anatomie`): ~100 analyses, 440 landmarks, each measure with construction/unit/norm/sd. FRWin cites NO author for anything, so a batch-wide sourcing call was made — the norm ships, no source is claimed (naming FRWin would be untrue and a copyright risk per Dirk; citing an unread paper is already forbidden), the `PUBLIC_ANALYSE` source string says exactly that, and it is INTERNAL (the card never renders `source`); a test forbids any measure/profile source naming FRWin. Steiner-specific norms ride as profile overrides; pure-formula measures with no two-line construction (Holdaway difference) are dropped, not guessed. The picker sorts by the TRANSLATED label (`orderProfiles` takes a resolver rather than importing `t`, so the pure module stays dependency-free), **favourites** first in their own group (`getCephFavourites`/`setCephFavourite`); the alphabetically-first favourite opens the card unless `isCephProfileChosen()` — a choice that changes under the user's hand is worse than no default. Favourites are a PRACTICE preference like the restoration palette: session state, never payload, and deliberately NOT in the blank-slate reset (`resetCephProfilePreferences()` is for a host that wants it). Ricketts brought five measures (facial depth, ML-FH, convexity, UK1 to A-Pog in mm and in degrees) and the one norm OVERRIDE that shows what the field is for: the facial axis is 90 ± 3.5 in Ricketts and 90 ± 3.0 in Paddenberg, so 93.3° reads inside one scatter and outside the other. Its norms are Dirk's own clinical figures and the `source` string SAYS SO in as many words ("the original publications have not been read here") — the sourcing rule demands a stated provenance, not a read publication, the same treatment `JARABAK_BANDS` gets; a test pins that wording so nobody later upgrades it to a citation. Jarabak added the gonial angle a SECOND time on purpose — `GnTgoAr` runs Gn-tgo-Ar, Jarabak's runs Ar-Go-Me, and two constructions are two measures, not one with two norms (else the two half-angles would have to sum onto a measure defined over different points; the profile override is only for the same measure under two schools). Its two half-angles ship with NO target although the literature gives figures, because it gives RANGES (52-55 / 70-75) and not a mean with a scatter — converting one into the other asserts a precision the source does not have. In `cephImport.ts` the Jarabak block must stay ABOVE `GnTgoAr`: first pattern wins, and `/kieferwinkel/i` would swallow "Kieferwinkel, oberer Teil".
- **Skeletal age (c51.4)** — `src/skeletalAge.ts`, pure/dependency-free like `cephalometry.ts`. "How much growth is left", read TWO ways kept separate so the record says which: **CVM** (cervical vertebral maturation, Hassel & Farman, 6 stages) off the SAME ceph film, and **Fishman SMI** (11 stages, Dirk's choice for the hand-wrist film 22.08.2026) off the hand radiograph — the hand film is the gold standard and is NOT in FRWin. They share one language because the 11 SMIs map onto the 6 CVM stages in fixed pairs (`smiToCvm`), so a hand stage resolves to a CVM stage and the same remaining-growth band. `deriveSkeletalMaturity({cvm,smi})`: the DIRECTLY-read CVM beats the hand-mapped one, and a conflict is REPORTED (`disagree`) not resolved, like c51.2's sagittal individual-vs-population. Bands + the SMI↔CVM table are from Erdmann 2007 (Münster, Kap. 2.2, after Hassel & Farman; original not read, `SOURCE_SKELETAL` says so). Session state (`getCvmStage`/`setCvmStage`, `getHandSmiStage`/`setHandSmiStage`, in the blank-slate reset) — no payload, no FHIR, no svgLayer. Rendered as a section beside the growth pattern in `CephalometryCard`.
- **Photostatic — Powell (c51.3)** — profile-PHOTO angles from the FRWin catalogue, folded INTO the cephalometry card (Dirk's "Bau A") but marked as a different MEDIUM: `CephMeasure.medium`/`CephProfile.medium` = `"film"` (default) | `"photo"`, Powell is `photo`. The picker groups by medium (Cephalometry vs Photostatic, favourites-first within each — `orderProfiles` takes a profile subset), so the record says whether a soft-tissue value was read off the film or the photo (the bead's overlap requirement). Eight measures + 3 soft-tissue landmarks (gb/ce/ctg); face-height ratios dropped like Holdaway; source `PUBLIC_ANALYSE`, session state, no payload/FHIR.
- **SOURCING RULE, enforced by a test** — every measure carries a mandatory `source`, and a norm without a publication is NOT shipped (`norm`/`sd` stay `null` and the UI shows no target). Norms come from Paddenberg et al. 2021 and from Segner & Hasund 1998 as tabulated by the Regensburg clinic; classification rules and both clinical equations come first-hand from Habersack & Hasund's own manual. Two conflicts are left VISIBLE rather than resolved (Paddenberg gives ML-NSL ± 2,0 against Segner's ± 6,0; the two also differ on SNA/SNB means).
- **FHIR coding lives on the measure** (`coding: { local, ucum, loinc?, snomed? }`), not in a later mapping table — the same inline pattern `ClinicalAxis.finding` / `AxisValue.coding` already uses, so there is no second layer to drift. No LOINC or SNOMED code is invented; none verified for a cephalometric measurement could be produced, mirroring `toFhirPerio.ts`'s treatment of per-site BOP and the Mombelli indices.
- **Derivations** — `deriveJawRelation` (facial type after Björk with Hasund's limits, harmony, and the sagittal class reported TWICE: against the individual norm and against the population one, because their disagreement IS the finding); `deriveGrowthPattern` (a vote across every indicator with a sourced norm, each reporting its deviation, its own reading and whether a `published-band` or the `standard-deviation` fallback decided it, plus a `dissent` count; an empty form is `indeterminate`, not `neutral`); `individualisedAnb` / `individualisedAnbExtended` / `individualisedWits` (Paddenberg 2021 — deliberately NOT the classical coefficients the practice software runs, whose publication has not been read).
- **Import (`src/cephImport.ts`)** — `parseCephText(text)` takes TEXT, never a PDF: pasting works with no dependency and a PDF reader would feed the same parser. Returns per-line `confidence` (`high` only when the full norm/measurement/deviation triple is present, so the SECOND number is unambiguously the measurement) plus every `candidate` number. **Nothing is applied without confirmation** — a printed sheet has rows carrying only a norm, and an importer grabbing the first number would file a norm as a finding. The number regex uses a lookbehind because cephalometric labels are full of digits (`OK1-UK1`).
- **Persistence** — tooth widths (`getToothWidths`/`setToothWidth`), the four occlusal readings (`getOcclusalMeasurements`/`setOcclusalMeasurement`), cephalometric values (`getCephValues`/`setCephValue`) and the active profile are SESSION state, deliberately outside the export payload: c51's audit found no published Dental Core carrier, and c51's rule is to stay blocked rather than invent a local-code path. Payload version, FHIR bundle and SVG fingerprints are unchanged, and tests pin that boundary. The promotion point is marked in `odontogram.ts`.
- **UI** — `ModelAnalysisCard.tsx` (arch + list, switchable, one record) and `CephalometryCard.tsx` (profile selector, live norms, paste importer, jaw-relation and growth panels). Both live in the **third clinical view** (Dirk, 22.08.2026 — the switcher's German label is `KFO`), beside Odontogram and Periodontal Status. The switcher `#appViewToggle` is no longer gated on `perioViewMode` as a whole: the orthodontic view has NO popup housing, so in popup mode the switcher stays and only the PERIODONTAL segment goes (the launch button beside it opens that one as a dialog). `.ortho-column` spans both grid columns with the right control panel hidden beside it — hidden, never unmounted, exactly like the odontogram column, for `wireControls()`'s one-time listeners and for fingerprint parity — and it lays the two cards side by side from 1400 px, because measured at 1900 px one full-width card puts 900 px of nothing between a number and the bar that shows it. `npm run prototype:model` still opens a bench. Both use `type="text"` with `inputMode="decimal"`, NOT `type="number"` — a number input silently discards the decimal comma every German-speaking user types.

## Befundeingabe ueber Kuerzel (bead odontogram-t8y)
- **`src/shorthand.ts` is DOM-free and imports nothing from `odontogram.ts`**, like `retention.ts` and `perioClassification.ts`. The bead asks for THREE entry routes onto the SAME finding set — keystrokes, a FHIR query against a practice system, speech — so the table and parser live where all three can call them; a table inside a key handler grows a second table beside it. `odontogram.ts` imports FROM it (`ARCH_ROWS`, `nextChartTooth`, `parseShorthand`, `shouldCommit`, `dentureValueFor`, `teethBetween`), never the reverse.
- **The table is TRANSCRIBED, not invented** — from charly's 01-Befund keypad, recorded with both screenshots in `docs/charly/01-befund-tastenfeld.md`, meanings resolved by Dirk. `SHORTHAND_DE` is per language from the start (`k` for Krone is German; the library ships twelve UI languages).
- **Two properties the keypad forces, each pinned by a test:** LONGEST MATCH and CASE SENSITIVITY (`d` distal vs `D` eruption stage; `t` telescope vs `TK` onlay; `K` Kunststoff vs `k` Krone vs `K3` caries stage), and THE MATERIAL COMES FIRST and stays — a mode, not a suffix. The keypad's LABELS (`Am`, `Kst`, `Ker`, `GIZ`) are deliberately NOT typable: accepting them makes `A`+`m` (mesial) indistinguishable from `Am` and silently swallows the surface. The keys are the single capitals `A K G E`.
- **One material key has TWO readings** (`MATERIALS`), because `fillingMaterial` and `restorationMaterial` have different value spaces: `K mo` is a composite filling, `K k` a crown in Gradia. Where a reading is absent (amalgam as a restoration) nothing is invented.
- **`shouldCommit(buffer)`** decides whether a keystroke applies at once (six anteriors marked + `k` is the whole gesture) or waits: it commits only when the last key is a finding on its own AND no longer key begins with it. A run opener (`c`, a surface) always waits — committing `c` early would make the surfaces that follow read as a FILLING.
- **`e` emits `{kind:"denture"}` without an extent**; `dentureValueFor()` decides partial vs full from how much of the arch is selected. `b` (Brueckenglied) is `restorationType`, `e` (Prothesenzahn) is `prosthesis` — the registry forbids both on one tooth.
- **The Tab walk moves the SELECTION, not just the focus**, so the tooth one stands on is highlighted by the existing `.active` styling — no second notion of "current tooth". `CHARTING_ORDER` goes AROUND THE MOUTH (18-28, then 38-48, wrapping) and is NOT the display order flattened: the lower row is drawn 48→38 and walked 38→48. The arrow keys are untouched — they are the map (two rows, spatial, no wrap), Tab is the round.
- **Seven keys are understood with no axis yet** (`+ - ? p Fra Hem D`), listed in `SHORTHAND_PENDING` with the bead that will give each a target (odontogram-fu1/-t6y/-ca0/-0n8). They are reported as `pending`, never as `unknown`: a typo and a missing axis are different situations and the read-out says which.
- Everything applies through `applyToSelected`, hence the DS-1 gate and the whole selection. No new mutation path, no new state field, payload unchanged.
- **Two switches, Settings -> "Kuerzel"** (`shorthandEnabled`, `shorthandTabWalk`; `get`/`set` pairs in `odontogram.ts`, session state like `perioViewMode`). Zoltan Dul's condition on the upstream issue, 19.08.2026: keyboard entry "has to be flexible and fully configurable in Settings, never hard-wired". He is right past the upstream question — typing letters on a tile is additive (nothing else uses those keys), but the Tab walk OVERRIDES a standard navigation key. OFF means off: no keystroke lands and Tab is not `preventDefault`ed, so it leaves the chart as it does everywhere else. `setShorthandEnabled(false)` calls `resetShorthandInput()` — a half-typed key or a standing material mode must not survive the switch, or the next crown after switching back on is silently gold. Both default ON in this fork (Dirk asked for them); a host wanting upstream's default flips them at mount. The key table is rendered IN the tab, labelled from the registry's own `uiOptions[].labelKey` — no second copy of the copy in twelve languages.

## Zaehne markieren (bead odontogram-apn)
- **A span follows the ARCH, not the geometry** (`teethBetween` in `shorthand.ts`, beside the arch table the Tab walk and the arrow keys also read). A rectangle over the tile centres picks up the opposing jaw as soon as the pointer strays. Across the midline (13→23) yes; across the jaw never.
- **The anchor stands still** (`selectionAnchor`), set by every plain selection — click, Tab step, unshifted arrow. Shift+arrow right then left must SHRINK the span again, which only works if the far end stays put.
- `pointerdown/-move/-up`, not `mouse*`, so mouse and stylus share one path and the existing touch gestures stay untouched. A 4 px threshold keeps a click a click; the click that follows every `pointerup` is suppressed once, or the span collapses back to one tooth. Escape during a drag restores the previous selection.
- Pure operation: everything still runs through `selectedTeeth` + `updateSelectionUI()`, so the batch actions and the DS-1 lane are untouched.

## Chart State Model (Status vs Plan)
- **Status→Plan edit propagation (DS-1):** a per-tooth runtime `Set planEditedTeeth` marks teeth explicitly edited while in Plan mode. ALL interactive tooth edits route through a central gate — `gateToothEdit(toothNo, applyFn)` (single) / `gateToothEditBatch(toothNos, applyFn)` (atomic over a set; `applyStatusExtra`/`applyToSelected`/`setEdentulous`/dentition presets use it). Logic: **plan mode** → `applyFn()` + mark the tooth; **status mode, tooth NOT plan-edited** (or plan uninitialized) → `applyFn()` + `mirrorStatusToPlan(toothNo)` (deep copy via serialize→hydrate) so the plan tracks the corrected reality and the tooth shows NO diff; **status mode, tooth IS plan-edited** → a **blocking in-app confirm** (`src/DualStateConfirm.tsx`, mirrors SettingsModal) BEFORE applying — accept applies to status only (plan stays → they diverge, the diff shows it), cancel applies nothing + reverts the control. Batches confirm ONCE over the whole set and apply all-or-none. `applyFn` returning `false` (no-op) skips marking/mirroring. `planEditedTeeth` is runtime-only (NOT serialized) and cleared on plan (re)init / reset / import / `setPlanChart`. NON-interactive paths (import/hydrate, reset/clear buttons, `cloneChart`, lazy `defaultState()` vivify) are NOT gated. Parity byte-identical (edit-routing only).
- Two parallel per-case states, `charts.status` and `charts.plan` (both `Map<toothNo, ToothState>`, declared as `const charts: Record<"status" | "plan", Map<...>>` in `src/odontogram.ts`). `toothState` is a module-scoped, REASSIGNABLE `let` alias pointing at whichever chart is currently active — every pre-existing `toothState.get/set/...` call site keeps operating on the active chart unchanged.
- `chartMode: "status" | "plan"` tracks the active chart (default `"status"`). `getChartMode()`/`setChartMode(mode)` are the public read/switch API; `setChartMode()` reassigns `toothState`, does a full repaint of every tooth (reusing the same repaint loop `importStatus()` uses — no new render path), and syncs the header toggle UI.
- The plan chart is lazily initialized: the FIRST time `setChartMode("plan")` is called, `charts.plan` is deep-copied from `charts.status` via the existing `serializeState → hydrateState` round-trip (`cloneChart()`), guaranteeing independent Maps/Sets so edits never leak between charts. Later switches reuse whatever is already in `charts.plan` — it is never re-cloned from status once initialized.
- UI: a `Status | Plan` segmented toggle (`#chartModeToggle`, buttons `#chartModeStatus`/`#chartModePlan`) sits in the dental-chart card header (`src/App.tsx`); the active chart also gets a `.plan-mode` class on the chart card as a visual cue when Plan is active.
- Per-state public API (independent of which chart is active): `getStatusChart()` / `getPlanChart()` return each chart's payload (`{version, globals, teeth}`); `setPlanChart(payload)` hydrates the plan chart only (status untouched), repainting the DOM only if plan is the currently active mode.
- Export/import stay status-primary: `exportStatus`/`exportFhir`/file import always target `charts.status` explicitly, never the active-chart alias — exporting while in Plan mode still yields the status chart. The JSON export gains an additive top-level `plan` field, emitted only when the plan chart is initialized AND differs from status; payload version bumped to **2.11** (imports still accept legacy 1.4–2.10). Import restores `plan` when present; its absence clears/uninitializes the plan chart (never resurrects a stale plan from before the import).
- FHIR export/import remain status-only — `buildFhirBundle()`/`parseFhirBundle()` are unaffected by the plan chart; there is no FHIR representation of the plan chart yet.
- Render is byte-identical to the pre-dual-state single chart (`parity.test.ts` SVG fingerprints) — the toggle only changes WHICH chart is drawn, never how a chart renders.
- **Proposed styling (plan-only render):** in Plan mode, any SVG layer active in the plan chart but NOT in the status chart for that tooth (a finding the plan *adds*) renders with a distinct dashed, tinted "proposed" outline. `applyProposedStyling(toothNo, svg)` runs in `applyStateToSvg`'s loop AFTER `applyStateToSvgSingle` (never inside it — it clones the svg and re-invokes `applyStateToSvgSingle` to render the status state, which would recurse): it computes `planIds ∖ statusIds` (status rendered into `svg.cloneNode(true)` via `applyStateToSvgSingle(toothNo, clone, charts.status.get(toothNo) ?? defaultState())`, then `collectActiveLayers`) and marks the plan-only layers via the **inline-style channel** (`style.strokeDasharray` + a `style.stroke` tint) — never `style.opacity` or a CSS class, the two channels `collectActiveLayers` fingerprints. Gated on `chartMode === "plan" && planInitialized`; `clearProposedStyling` runs first on every call and restores each captured `data-base-dash`/`data-base-pstroke` (symmetric reset, so switching back to Status or editing a plan finding to match status leaves no stray dashes). A `#proposedLegend` ("dashed = proposed") shows via pure CSS under the chart card's `.plan-mode` class. Status-mode render + parity capture never run this branch → byte-identical.
- **Status→Plan diff:** `getPlanChanges()` returns a pure, read-only diff of the two charts — `PlanChange[]` (`{ toothNo, axis, from, to }`), one entry per tooth per treatment axis whose human-readable label differs between `charts.status` and `charts.plan`; `[]` when the plan is uninitialized. It compares over `DIFF_AXES` (presence, substrate, restoration, prosthesis, crownAction, ortho, pulpEndo, apical), each described by the SAME label helper the tooltip/summary already use (no reinvented copy). The list is also exposed on `getOdontogramSummary()` as `plannedChanges`; `App.tsx` renders it as a distinct "What changes" box (`#plannedChangesBox`) under the Tooth-information panel, shown only when non-empty. No render/state/payload change (parity byte-identical).

— der Abgleich ist ein eigener Schritt**, und ohne ihn sieht Malte nichts.

```
cd .beads/embeddeddolt/beads_odontogram
dolt pull --user dirk origin main     # ERST, sonst wird der Push abgelehnt
dolt push --user dirk origin main
```

Drei Dinge, die dabei jedes Mal auflaufen, wenn man sie nicht weiß:

- **`bd dolt push` funktioniert nicht.** Es meldet sich als `root` an und
  scheitert. Der Benutzername kommt AUSSCHLIESSLICH aus dem Schalter `--user`;
  geprüft am 2026-08-19: weder eine Angabe in der URL
  (`https://dirk@dolt.cognovis.de/…`) noch `DOLT_REMOTE_USER` / `DOLT_USER` /
  `DOLT_REMOTE_USERNAME` werden gelesen. Das Passwort kommt aus
  `DOLT_REMOTE_PASSWORD` (in `~/.zshenv` aus dem Schlüsselbund).
- **Immer erst `pull`.** Malte schreibt auf denselben Server. Ohne pull lehnt
  der Push mit `non-fast-forward` ab; der Merge selbst läuft dann örtlich und
  konfliktfrei durch.
- **Nicht `~/.beads/shared-server/dolt/…` benutzen.** Das ist eine alte Kopie,
  auf die die ursprüngliche `bdsync`-Funktion noch zeigte — Schreibvorgänge
  dorthin landen nirgends.

Die `events`-Tabelle fehlte in dieser Datenbank vom 2026-08-16 bis 2026-08-18
(ein Schema-Unfall unter `bd` 1.2.1 hatte sie fallen lassen), wodurch JEDER
`bd`-Schreibvorgang mit `table not found: events` abbrach. Sie wurde aus
`HEAD~3` samt 248 Zeilen Prüfspur zurückgeholt. Bricht ein `bd`-Befehl wieder
so ab: die Tabelle ist in einer frisch angelegten Datenbank derselben Version
enthalten, `show create table events` dort liefert die Definition wörtlich.

**`events` steht auf `bd`s eigener Ausnahmeliste** (`select * from dolt_ignore`
— neben `leases`, `repo_mtimes`, `local_metadata`). Sie wird also absichtlich
weder committet noch übertragen: die Prüfspur ist ÖRTLICH. Deshalb erscheint
sie in keinem Commit, deshalb meldet `dolt status` nichts Offenes, obwohl
`select count(*) from events` Zeilen liefert — und deshalb repariert ein Push
von hier auch keine fremde Kopie. Wem die Tabelle fehlt, der muss sie bei sich
anlegen.

## Conventions
- Tooth IDs use FDI notation (11-48) as internal keys
- All user-facing strings go through `src/i18n/translations.ts`
- SVG layers follow naming: `{toothId}_{surface}.svg`
- State is serialized as JSON for storage/transfer
- Read-only mode is supported via `readOnly` prop
- Keyboard accessibility (WCAG) is implemented for tooth navigation

## Documentation (mandatory)
- Updating the documentation is **mandatory** for every user-facing change (new
  feature, changed behavior, new/renamed public API, new state field or enum value).
- Keep `CHANGELOG.md` current — add an entry (Keep a Changelog format) and bump the
  version in `package.json` and the README version badge for each release.
- **English is the source of truth** for the README; translate the others from it.
- Maintain a README for **every UI language the program supports** (currently
  HU, EN, DE, ES, IT, SK, PL, RU, PT-BR, AR, ZH, FR — see `Language` in
  `src/i18n/translations.ts`). `README.md` is the English top level and links all twelve; the per-language guides live
  in `lang/README-<code>.md` (e.g. `lang/README-de.md`, `lang/README-pl.md`,
  `lang/README-ru.md`, `lang/README-ar.md`, `lang/README-zh.md`). When a new UI
  language is added, add its README too and update every language switcher.
- **RTL:** Arabic (`ar`) is the only RTL language. The document root `dir`
  attribute reacts to the active language (`rtl` for `ar`, `ltr` otherwise), so
  the whole UI mirrors; the dental chart (`#toothGrid`) and the periodontal
  charts are explicitly pinned `dir="ltr"` (attribute + CSS) so tooth
  geometry/numbering never flips.

## Scope Control
- Do not add dependencies on external dental systems or APIs
- Do not add routing — this is a single component, not an app
- Keep the bundle size minimal — no heavy libraries
- SVG assets should be optimized (no unnecessary metadata)
